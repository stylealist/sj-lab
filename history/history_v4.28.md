## 1. 무엇이 느린가

지도에서 아파트를 누르면 그 단지의 평형·추세·거래 내역을 조회합니다. 그런데 **단지 키에
인덱스가 없어** 지금은 **시군구 전체를 읽은 뒤 단지를 골라냅니다.**

오늘 실제로 재어 본 결과(수원시 영통구의 단지 한 곳, 전월세 거래 내역):

```
Parallel Bitmap Heap Scan on apt_rent
  Recheck Cond: sgg_cd = '41117'      ← 시군구로만 좁힌다
  Filter: apt_seq = '41117-1'
  Rows Removed by Filter: 118,800     ← 읽고 버린 행
Buffers: read 4,994 블록 (약 39MB)
Execution Time: 1,870 ms
```

**122건을 돌려주려고 12만 행을 읽고 버립니다.** 그래서 **새 지역에서 단지를 처음 누를 때마다
약 2초**가 걸립니다(같은 지역 두 번째부터는 디스크 캐시 덕에 0.05~0.15초).

어제 만든 전국 검색 때문에 **다른 지역 단지를 바로 고르는 일이 많아져** 이 2초를 더 자주 만나게
됐습니다. 그리고 오늘 고친 **전월세만 있는 단지 3,053개**의 상세도 같은 방식으로 찾으므로
수혜 대상이 늘었습니다.

## 2. 인덱스 2개로 없어집니다

```
(sgg_cd, apt_seq, deal_year DESC, deal_month DESC)   ← 매매 · 전월세 각각
```

- **코드는 고칠 것이 없습니다** — 지금 쿼리가 그대로 이 인덱스를 탑니다
- **용량과 맞바꿉니다** — 둘 합쳐 **약 550~650MB**(같은 표의 `(시군구, 연, 월)` 인덱스가
  전월세 213MB·매매 119MB 이고 거기에 단지 키 한 칸이 붙는 정도입니다)
- **만드는 동안 수집(쓰기)이 막히지 않게** `CONCURRENTLY` 로 만듭니다 — 그래서 **한 줄씩,
  트랜잭션 밖에서** 실행해야 합니다
- 되돌리기는 `DROP INDEX CONCURRENTLY` 한 줄이고, 지워도 화면은 그대로 동작합니다

**실행은 사용자가 합니다**(DDL — 프로젝트 규칙). 스크립트는
`db/estate/estate_apt_complex_index.sql` 에 있고, 실행 전/후 확인 쿼리와 되돌리기까지 그 안에
적혀 있습니다.

## 3. 실행하다 막힌 것 — 툴이 트랜잭션으로 감쌉니다

DB 툴에서 `CREATE INDEX CONCURRENTLY` 를 실행하니 거부됐습니다.

```
SQL Error [25001]: ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

툴이 기본으로 **수동 커밋**이라 문장을 트랜잭션으로 감싸기 때문입니다 — 스크립트 문제가 아니라
**실행 모드** 문제입니다. 커밋 모드를 바꾸지 않고 가는 길로 **`CONCURRENTLY` 를 떼고** 했습니다.

| | `CONCURRENTLY` | 떼고 실행 |
|---|---|---|
| 조회 | 영향 없음 | **영향 없음**(SHARE 락은 읽기와 충돌하지 않습니다) |
| 쓰기(수집) | 영향 없음 | 만드는 동안 대기 → **그 시간대에 수집이 없었습니다**(cron 06:00·07:00) |
| 속도 | 느림(표 2회 읽기) | **빠름**(표 1회 + 병렬) |
| 중단되면 | 못 쓰는 인덱스가 남음 | **깔끔히 롤백** |

> **제가 한 번 틀렸습니다** — 처음에 락을 `ACCESS EXCLUSIVE` 라고 했는데 실제로는 **SHARE** 입니다.
> 조회가 멈추는지 아닌지가 갈리는 차이라 바로 정정했습니다.
>
> **진짜 위험은 "만든 뒤"였습니다.** 수동 커밋 툴에서는 인덱스가 다 만들어져도 **커밋할 때까지
> 락이 유지**되고, 이 DB 는 `idle_in_transaction_session_timeout`·`lock_timeout` 이 **둘 다 0**
> 이어서 무한정 기다립니다. 커밋 없이 세션을 닫으면 작업이 날아갑니다 — 그래서 스크립트에
> "★ 여기서 Commit ★" 을 박아 두었습니다.

## 4. 결과 — 재어 봤습니다

**DB 쿼리**(같은 쿼리, 수원시 영통구 단지 한 곳 전월세)

| | 계획 | 시간 | 읽은 블록 |
|---|---|---|---|
| 전 | 시군구 훑고 `apt_seq` 걸러내기(118,800행 버림) | **1,870ms** | 4,994 |
| 후(첫 조회) | **Index Scan using ix_apt_rent_complex** | **33ms** | 121 |
| 후(두 번째) | 같음 | **0.4ms** | 디스크 읽기 없음 |

매매 쪽도 같습니다 — 청주 흥덕구 단지 500건이 **0.9ms** 이고, 인덱스 순서가 조회 순서와 같아
**정렬도 필요 없습니다.**

**운영 화면 기준**(처음 누르는 지역의 단지 상세)

| | 시간 |
|---|---|
| 전 | 약 **2초** |
| 후 — 청주 흥덕구 · 경주시(이번에 처음 누름) | **160~190ms** (두 번째 70ms) |
| 후 — 전월세만 있는 단지(어제 고친 경로) | **96ms** |

**용량은 예상보다 적었습니다** — 둘 합쳐 **377MB**(`ix_apt_trade_complex` 189MB ·
`ix_apt_rent_complex` 188MB). 제 추정은 550~650MB 였습니다. 둘 다 `valid` 입니다.

**코드 변경은 없습니다** — 기존 쿼리가 그대로 새 인덱스를 탑니다.
