## 한 줄 요약

**10개월 멈춰 있던 공공데이터 수집을 되살리고**, 아파트 실거래 20년치를 새 스키마로 받아
**허브에서 들어가는 네 번째 사이트**를 만들었습니다.

## 1. 수집이 멈춰 있었습니다 — 10개월째

아파트 데이터가 2025-12에서 끊긴 걸 발견하고 원인을 찾았습니다. **키가 만료된 게 아니었습니다.**

서비스 키가 이미 URL 인코딩된 형태인데 코드가 **한 번 더 인코딩**해서 공공데이터포털이 403을
돌려주고 있었습니다. 버스 노선 수집만 이 검사를 하고 있어서 혼자 살아남았고, 그래서
"아파트만 멈춘 것"처럼 보였습니다.

| 수집 | 마지막 적재 | 상태 |
|---|---|---|
| CCTV · 버스 노선 | 최근 | 정상(검사 있음) |
| **약국 · 병원** | 2025-12-18 | **함께 멈춰 있었음** |
| **아파트 매매 · 전월세** | 2025-12-26 | **함께 멈춰 있었음** |

한 줄 수정으로 **네 개가 같이 복구**됐습니다. 키 처리를 한 곳(`serviceKeyParam()`)으로 모았습니다.

## 2. 백필이 구조적으로 불가능했습니다

키를 고쳐도 과거 데이터가 들어오지 않았습니다. 적재 코드가 **"오늘로부터 30일 안"** 거래만
골라 넣고 있었습니다 — API 는 데이터를 주는데 **코드가 받아 와서 버린** 것입니다.

```
2026-05~08  API 응답 있음(강남구 474·226·169·94건)  →  적재 0건
수정 후     202605 → 45,226건 적재
```

중복 방지용 장치였는데, 새 표의 **유니크 인덱스가 그 일을 정확히** 하므로 걷어냈습니다.
덕분에 매일 도는 cron 도 정확해졌습니다(전에는 30일 넘어 들어온 늦은 신고분을 영구히 놓쳤습니다).

## 3. estate 스키마로 분리

아파트 데이터를 `ai` 에서 `estate` 로 옮겼습니다. `ai` 는 앞으로 AI/RAG 표만 둡니다.

| | 내용 |
|---|---|
| 표 | `estate.apt_trade` · `estate.apt_rent` (컬럼 주석 전체 포함) |
| 중복 방지 | 자연키 유니크 인덱스 `NULLS NOT DISTINCT` + `ON CONFLICT DO NOTHING` |
| 집계 뷰 | `v_apt_trade_monthly` · `v_apt_rent_monthly` (월·지역별 건수·평균·중위) |
| 스크립트 | `db/estate/estate_apt.sql` (담당자 실행 완료) |

**중복이 실제로 쌓여 있었습니다** — 옛 표의 2025-11 매매에서 2.6%가 중복이었습니다.
유니크 인덱스를 넣은 뒤 같은 달을 다시 받아 **0건**임을 확인했습니다.

## 4. 20년치 받기

이번 달부터 **1개월씩 과거로** 내려가며 받고, 12개월 연속 0건이면 멈추는 방식입니다.

```
2026-10 → 2006-01   매매
2026-10 → 2011-01   전월세 (데이터 시작점에서 자동 정지)
```

3일에 걸쳐 받으며 중단이 여러 번 있었지만 **모두 커서로 복구**했습니다.

| 중단 | 원인 | 대응 |
|---|---|---|
| 2회 | API 일일 한도(429) | 20분 대기 후 같은 구간 재시도 — 커서를 전진시키지 않음 |
| 1회 | 로그 쓰기 오류로 드라이버 사망 | 로그 실패를 치명적으로 보지 않게 수정 |
| 1회 | 재기동 순서 실수(제 실수) | 완료 감시기가 새 스케줄러를 죽임 → 순서 문서화 |

**받은 결과 (완료)**

| | 매매 | 전월세 |
|---|---|---|
| 건수 | **9,911,036건** | **11,494,802건** |
| 기간 | 2006-01 ~ 2026-10 (**250개월, 빈 달 없음**) | 2011-01 ~ 2026-10 (190개월) |
| 용량 | 4,002 MB | 4,915 MB |

합계 **8.7 GB** · 220개 시군구. 연도별로 세어 **모든 해가 12개월 완비**임을 확인했습니다
(2026년만 10개월 — 올해가 10월까지라 정상).

받다가 한 달 빠졌던 `201509` 매매도 다시 받아 **50,278건**을 채웠습니다.

## 5. 조회 API — fast-api-ai 를 실제로 쓰기

골격만 있던 `fast-api-ai` 에 부동산 조회 라우터를 붙였습니다. Eureka·게이트웨이 경로가 이미
살아 있어 **추가 인프라가 필요 없었습니다.**

`/fast-api-ai/estate/` 아래 7개 — 상태 · 데이터 범위 · 지역 목록 · 매매 월별 추세 ·
전월세 월별 추세 · 거래 목록 · 지역 순위.

- **읽기 전용 계정**으로만 접속하고, 접속 설정이 없으면 **이 라우터만 503**이고 나머지는 정상
- 지역명은 `public.g_sgg` 와 조인해 내려줍니다(코드가 100% 매칭)

## 6. 신규 사이트 — 허브의 네 번째 카드

`sj-lab-estate-web` 을 새로 만들었습니다. **API 센터와 똑같은 구성**(React 18 + Webpack,
인라인 스타일, 로그인 게이트 복제)이라 기존 세 사이트와 이질감이 없습니다.

- 요약 카드 4개 → 조건(지역·기간·단지명) → **매매 / 전월세 / 지역 순위** 탭
- 차트는 **외부 라이브러리 없이 인라인 SVG** — 의존성을 늘리지 않았습니다
- 허브의 `Lab` 자리를 **"부동산 실거래"** 카드로 교체(로컬 4200)

## 남은 이야기

- **속도는 표가 커지며 느려집니다**(4.1분/월 → 12분/월). 조회용 인덱스를 떼면 빨라지지만
  1,000만 행에서는 `DROP INDEX` 자체가 오래 걸려 이번엔 하지 않았습니다
- 서비스 키가 저장소와 대화에 노출돼 **교체 대상**입니다. 지금은 환경변수로만 주입하도록 바꿨습니다
- **운영 배포는 아직 하지 않았습니다** — Jenkins 잡과 정적 경로(`sj-lab.co.kr/estate/`), 그리고
  운영 DB에 `db/estate/estate_apt.sql` 실행이 필요합니다(지금은 개발 DB만)
- `sj-lab-estate-web`은 **신규 저장소라 GitHub 원격이 없습니다** — 로컬 커밋까지만 해 두었습니다
- 공개 API(`sj-lab-openapi`)에 부동산 데이터를 열지는 아직 판단하지 않았습니다
  (`docs/openapi-expose-checklist.md` 기준으로 보면 조회·무인증·비민감이라 열 수 있지만,
  건수가 많아 기간·지역 필터를 필수로 둬야 합니다)
