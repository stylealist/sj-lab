## 1. 무엇이 문제였나

전국 아파트 단지 **44,616개 중 3,053개(6.8%)는 전월세 거래만** 있습니다. 지난주(11/17)에
그 단지들의 **상세 화면**은 열어 뒀는데, **지도 핀은 매매 기록만 보고 있었습니다.**

그래서 그 단지들은 **지도에 아예 뜨지 않았습니다.** 들어갈 길이 이름을 알고 검색창에 치는 것뿐이라,
사실상 "데이터는 있는데 찾을 수 없는 단지"였습니다.

## 2. 한 일

**지도 핀에 올렸습니다.** 매매 기록이 없으면 전월세 기록으로 핀을 만듭니다.

| | 매매가 있는 단지 | 전월세만 있는 단지 |
|---|---|---|
| 말풍선 색 | 파랑 | **청록** |
| 윗줄 | 34평 | **34평 전세** / 34평 월세 |
| 아랫줄 | 12.5억 (매매 평균) | **5.5억** (보증금) / 1억/120 (보증금/월세) |

- **색을 같게 두지 않았습니다** — 모양·색이 같고 숫자만 다르면 보증금을 **매매가로 읽습니다.**
  반대로 모양까지 바꾸면 "다른 종류의 지점"으로 보여서, **색만** 바꿨습니다.
- 마우스를 올리면 **"매매 거래 없음"** 이라고 분명히 적습니다.
- 전세가 한 건이라도 있으면 **전세 보증금**을 적고, 월세뿐인 단지는 월세를 적습니다
  (두 금액을 함께 적으면 섞여서 읽히지 않습니다).

## 3. 느려지지 않게 한 두 가지

**① 전월세 기록은 필요한 단지에만 묻습니다.** 화면에 뜨는 단지 전부(최대 300개)에 대고 전월세를
세면 지금과 **같은 크기의 작업이 하나 더** 붙습니다. 필요한 단지는 6.8% 뿐이므로 **그 몇 개만**
골라 묻습니다 — 보통 한 화면에 0~20개입니다.

**② 단지를 고르는 순서를 고쳤습니다.** 종전에는 **매매 건수 순**으로 골라 limit 까지 잘랐는데,
전월세만 있는 단지는 매매가 0건이라 **항상 꼴찌**였습니다. 서울처럼 단지가 많은 곳에서는 잘려 나가
핀에 오를 기회조차 없었습니다. 이제 **매매 + 전월세 건수**로 셉니다(전국 검색의 인기 순서와 같은 기준).

**철거된 옛 단지를 빼는 규칙은 그대로**입니다 — "고른 기간에 거래가 있는 단지만" 올리고,
이제 그 거래를 매매 **또는** 전월세로 봅니다.

## 4. 확인한 것 · 확인하지 못한 것

확인한 것

- 백엔드 **스모크 테스트 통과** — 쿼리 XML 파싱과 서비스 기동
- 프론트 **`npm run build` 통과**

**확인하지 못한 것 (중요)**

- **실제 데이터로 돌려 보지 못했습니다.** 작업 시점에 로컬이 꺼져 있고 DB 조회(MCP)도 붙지
  않았습니다. 즉 **쿼리가 의도한 결과·속도를 내는지는 아직 측정 전**입니다.
- 로컬을 띄우신 뒤 아래 두 가지를 보면 끝납니다.
  1. 서대문구 연희동 근처에서 **청록 말풍선**이 보이는지(예: 덕운포레스트힐)
  2. 지도를 옮길 때 핀이 **종전과 비슷한 속도**인지(종전 실측 200~570ms)
