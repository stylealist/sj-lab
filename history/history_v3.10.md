## 왜 필요했나

지금은 백엔드에 조회 기능을 만들고 공개 API에 여는 것을 **나중에 따로** 하고 있었습니다.
미루면 "백엔드에는 있는데 공개 API에는 없는" 상태가 쌓여, 외부에 열려 있는 범위가 무엇인지
아무도 모르게 됩니다.

## 만든 것 — 판단과 절차를 한 장으로

`docs/openapi-expose-checklist.md` 한 문서에 **열지 말지 판단 → 어떻게 추가 → 어떻게 확인**까지 담았습니다.

**① 열어도 되는가 (네 가지 모두 만족해야)**

| 조건 | 왜 |
|---|---|
| 조회(GET)다 | 공개 API는 조회만 엽니다 |
| 로그인·외부 계정이 필요 없다 | 공개 키 하나로 부를 수 있어야 합니다 |
| 응답이 과하게 크지 않다(또는 범위로 줄일 수 있다) | 전국 전체는 수십 MB라 시간을 넘깁니다 |
| 개인정보·내부 운영정보가 아니다 | 아무나 부를 수 있는 경로가 됩니다 |

열지 않는 것은 **쓰기·수정·삭제 전부, 사진 업로드, 첨부 파일 중계, 키 관리**입니다.
애매하면 열지 말고 먼저 물어보도록 적었습니다 — 한 번 열면 닫기가 어렵습니다.

**② 추가는 파일 한 개만**

`api-catalog.json` 에 항목 한 개를 더하면 끝입니다. 컨트롤러를 새로 만들지 않고,
**활용 페이지는 고치지 않아도 항목이 자동으로 늘어납니다.** 필드별 규칙(경로는 `/v1/`,
원천은 `/map/`, `apiKey` 는 넣지 않기 등)과 함께 고칠 문서(버전·계약 표·history)를 표로 정리했습니다.

**③ 확인**

테스트(`mvnw test`)와 실제 호출로 확인하는 항목을 적었습니다 — 정상 200, 필수값 빼면 400,
키 빼면 401, 모르는 파라미터는 400, 카탈로그와 활용 페이지에 보이는지.

자주 틀리는 것 네 가지(원천 경로 오타, DB 직접 조회 시도, 원천 경로 변경 후 미반영, 응답 가공)도
이유와 함께 남겼습니다.
