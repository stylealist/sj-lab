## 실행한 프롬프트

```
강남으로 나오는건 좋은데 다른 지역들도 조회할수있도록
시도, 시군구, 읍면동으로 나눠서 볼 수 있도록 해줘
```

## 1. 지역을 3단으로 고릅니다

**시 · 도 → 시 · 군 · 구 → 읍 · 면 · 동** 순서로 좁혀 봅니다. 위를 바꾸면 아래는 비워집니다.
첫 화면은 그대로 **서울특별시 · 강남구**로 시작하고, 동을 고르지 않으면 구 전체입니다.

- 시도 목록은 **시군구 목록에서 묶어** 만듭니다(서버가 시군구마다 시도 이름을 함께 주므로 호출이
  늘지 않습니다).
- 읍면동은 시군구를 고를 때 받아 옵니다. 선택지마다 거래 건수도 함께 보입니다.
- **지역 순위도 고른 시도 안에서** 냅니다 — 전국은 4.7초, 시도 범위는 0.6초입니다.
- 전국·시도 전체도 고를 수 있고, 느린 선택지에는 "몇 초 걸립니다"를 적어 두었습니다.

## 2. 재면서 두 가지를 고쳤습니다

**① 이름 조인을 무거운 집계에 넣었다가 되돌렸습니다**
시도 이름을 지역 목록 쿼리에 함께 묶었더니 **5.1초 → 19.7초**가 됐습니다. 이름은 17줄짜리 표에서
따로 읽어 서버가 코드로 붙입니다(비용 사실상 0). 이 교훈을 코드 주석과 문서에 남겼습니다.

**② 캐시가 만료되는 순간에도 기다리지 않게 했습니다**
전에는 기한이 지나면 그때 들어온 사람이 5초를 기다렸습니다. 이제 **가진 값을 바로 주고 갱신은
뒤에서** 합니다.

## 3. 속도 (로컬 실측, 화면 → 게이트웨이 → 서버 전 구간)

| 조회 | 시간 |
|---|---|
| 시군구+시도 목록 | 98ms |
| 읍면동 목록(강남구) | 72ms |
| 동 매매 추세(대치동) | 41ms |
| 동 거래 목록(대치동) | 62ms |
| 동 전월세 추세(대치동) | 814ms |
| 서울 시군구 순위 | 499ms |

읍면동까지 좁힌 조회는 **인덱스를 새로 만들지 않고** 기존 자연키 인덱스를 그대로 탑니다.

## 4. 작업하다 발견한 것 — 광주·전남 데이터가 없습니다

시도 목록을 만들다 보니 **17개 시도 중 15개만** 나왔습니다. 확인 결과:

| 시도 | 거래가 있는 시군구 |
|---|---|
| 광주광역시 | **0개** (행정구역 표에는 5개) |
| 전라남도 | **0개** (행정구역 표에는 22개) |

수집기는 행정구역 표를 그대로 순회하므로 **빠뜨릴 구조가 아닙니다.** 과거 데이터를 대량으로 받던
중 호출 한도에 막힌 구간이 조용히 넘어간 것으로 보입니다(그 함정은 `docs/backfill-workflow.md`에
적혀 있고, 뒤늦게 감지 기능을 넣었습니다).

- 그 두 시도는 화면에서 목록이 비어 보입니다.
- 다시 받으면 해결됩니다 — **전체 재수집이 아니라 27개 시군구만** 받으면 되므로 전체의 약 11%입니다.
- 언제 돌릴지 정해 주시면 진행하겠습니다(DB에 쓰는 작업이라 확인 후에 시작합니다).
